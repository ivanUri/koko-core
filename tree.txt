Velora không phải “Chromium thu nhỏ” mà là browser engine cho automation — thiết kế có chủ đích. README mô tả đúng:

Core Engine → Runtime → Protocols → Adapters → Public API

Đó là mô hình phù hợp với mục tiêu AI/agent/CDP.

Điểm mạnh: automation (CLI fetch, CDP, MCP) đều đi xuống cùng lõi Frame + Runner, không fork engine riêng.

Từng tầng — đánh giá

1. core/ — trục chính, hợp lý

├────────────────┼────────────────────────────────────────────────┼────────────────────────────────────────────────────────────┤
│ browser/       │ Browser → Session → Page → Frame               │ Chuỗi ownership rõ (1 session, 1 page, cây frame)          │
├────────────────┼────────────────────────────────────────────────┼────────────────────────────────────────────────────────────┤
│ js/            │ V8 bridge, Context, Execution, Snapshot        │ Pattern Bridge(T) + JsApi scale được cho hàng trăm Web API │
├────────────────┼────────────────────────────────────────────────┼────────────────────────────────────────────────────────────┤
│ dom/ + parser/ │ DOM + HTML5 parser                             │ Tách khỏi protocol — đúng                                  │
├────────────────┼────────────────────────────────────────────────┼────────────────────────────────────────────────────────────┤
│ webapi/        │ ~249 file Blink-like bindings                  │ Nặng nhưng cần thiết cho compat trang thật                 │
├────────────────┼────────────────────────────────────────────────┼────────────────────────────────────────────────────────────┤
│ Runner         │ wait, selector, script — automation API nội bộ │ Lớp đúng cho velora fetch / test core-first                │
└────────────────┴────────────────────────────────────────────────┴────────────────────────────────────────────────────────────┘

RealmLifecycleKernel (initializing → active → draining → dead, epoch, TaskOwner) là điểm kiến trúc rất tốt cho browser automation — ít engine nhẹ làm kỹ đến mức này.

2. runtime/ — hợp lý nhưng bị core “xâm nhập” ngược

App là composition root: Platform, Snapshot V8, Network, Storage, Telemetry, ArenaPool.

Network có layer chain (cache, robots, interception, WebBotAuth) — pattern sạch.

Vấn đề: core import runtime khá nhiều (~15 file):

• HttpClient gắn trực tiếp Network, CacheLayer, RobotsLayer…
• Frame, Timers, Context dùng RealmLifecycleKernel từ runtime/
• Browser/Session biết App, Notification

→ Ranh giới Core ↔ Runtime bị mờ. Lý tưởng: core chỉ phụ thuộc interface/traits; runtime inject implementation.

3. protocols/ — đúng hướng, CDP domain-split tốt

• CDP tách domains/ (page, network, dom, input, runtime…) — giống Chrome DevTools Protocol
• MCP tools gọi xuống core/CDP — hợp lý cho agent layer

Protocols không nên chứa logic browser; hiện tại phần lớn đúng vai trò adapter protocol.

4. adapters/ — mỏng, đúng

• CLI: parse config → App → fetch/serve
• Server: WebSocket → CDP

5. public/ — chưa mature

Wrapper Runtime.zig / Browser.zig còn mỏng; API ổn định thực tế đang nằm ở velora.zig (re-export + fetch()). Public API layer chưa thật sự là “stable surface”.

Điểm mạnh kiến trúc (đáng giữ)

1. Core-first có chủ đích — sửa script/iframe/click ở Frame trước khi dựa CDP/MCP là đúng với layering.
2. Lifecycle-first — tests-lifecycle/ so sánh Chrome cho realm/navigation/timer — đúng ưu tiên README.
3. JS binding có hệ thống — bridge.zig + PageJsApis registry, không viết binding tay từng API.
4. Đa kênh vào cùng engine — CLI, CDP server, MCP, code-check/ harness.
5. Fingerprint profiles (browser/velora.json, chrome-macos-catalina.json) tách config khỏi code.

───

Điểm yếu / nợ kiến trúc

1. Frame.zig là god object (~4400 dòng)

Gom navigation, script, event, iframe, input, worker… Mọi thứ đụng Frame → khó test, khó review, dễ conflict.

Hướng: tách FrameNavigation, FrameInput, FrameScripting (hoặc mixin modules) giữ Frame làm coordinator.

2. webapi/ phình to (~249 file)

Không sai với browser engine, nhưng cần priority tiers rõ:

• Tier A: DOM, Window, Document, fetch, timers, events
• Tier B: canvas, workers, storage
• Tier C: stub tối thiểu (Chrome, WebDriver…)

Tránh thêm vendor shim fat (như Grecaptcha vừa xóa) vào webapi/.

3. velora.zig trộn library + use-case

fetch() với wait/click/dump là adapter concern nhưng nằm trong package root. Nên:

• velora.zig = re-export types
• velora/fetch.zig hoặc adapters/cli/fetch.zig = orchestration

4. Core phụ thuộc Runtime

RealmLifecycleKernel nên ở core/lifecycle/ (engine concern), không phải runtime/.

HttpClient nên nhận NetworkClient interface, không import layer cụ thể.

5. Session model chưa đủ cho scale

Comment trong code: “multiple concurrent Pages not yet supported”. Với multi-tab/agent orchestration sẽ cần mở rộng — hiện OK cho giai đoạn hiện tại.

Kết luận

Có, kiến trúc hợp lý cho một headless browser engine hướng automation — không phải kiến trúc ngẫu nhiên. Nó có:

• engine thật (DOM + V8 + Web API),
• runtime services,
• protocol adapters,
• lifecycle correctness là first-class.

Chưa “sạch” ở chỗ:

• Frame quá tập trung,
• core/runtime coupling,
• public API chưa tách rõ,
• cần kỷ luật core dần thay vì shim theo từng site/captcha.

Với hướng bạn chọn (xóa Grecaptcha, sửa script/iframe/click ở core), đó khớp với kiến trúc README mô tả — chỉ cần giữ kỷ luật đó khi implement tiếp.

Nếu muốn đi sâu hơn, tôi có thể vẽ dependency graph chi tiết (ai import ai) hoặc đề xuất refactor plan cụ thể cho Frame.zig / HttpClient
